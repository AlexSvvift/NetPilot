# Архитектура NetPilot

## Общая схема

```text
Браузер
   |
   v
FastAPI routes  --->  Pydantic schemas
   |
   v
Repository  --->  SQLAlchemy  --->  SQLite
   |
   v
Scheduler  --->  Monitoring service  --->  HTTP / TCP / UDP targets
```

Приложение разделено на небольшие уровни:

- `api` принимает HTTP-запросы и превращает их в вызовы приложения;
- `schemas` проверяет входные и выходные данные;
- `repository` отвечает за чтение и запись в базу;
- `services/monitoring.py` знает, как проверять сетевые цели;
- `services/scheduler.py` запускает проверки по расписанию;
- `web` содержит простой интерфейс пользователя.

Такое разделение облегчает тестирование: сетевую проверку можно тестировать
отдельно от базы, а API - отдельно от оформления страницы.

## Жизненный цикл запроса

Например, пользователь добавляет HTTP-сайт:

1. Браузер отправляет `POST /api/targets`.
2. FastAPI передает JSON в `TargetCreate`.
3. Pydantic проверяет тип цели, URL, таймаут и интервал.
4. Route проверяет `X-API-Key`.
5. Repository создает запись `Target` в SQLite.
6. FastAPI возвращает JSON с созданной целью.
7. Scheduler позже получает активную цель и вызывает `check_target`.
8. Результат проверки сохраняется в `CheckResult`.
9. Следующий запрос dashboard показывает новый статус.

## Почему используется async

Сетевая проверка большую часть времени ждет: HTTP-сервер должен ответить,
TCP-порт должен принять соединение. Асинхронный код позволяет в это время
обслуживать другие проверки и запросы.

`asyncio.gather` запускает несколько проверок одновременно. Это особенно важно,
когда в панели десятки сайтов и серверов.

Операции SQLAlchemy в текущей учебной версии синхронные, поэтому планировщик
выполняет их через `asyncio.to_thread`, чтобы не блокировать event loop.

## Модель данных

Таблица `targets` хранит настройки цели:

- название;
- тип `http`, `tcp` или `udp`;
- URL либо host/port;
- таймаут;
- интервал;
- признак активности.

Таблица `check_results` хранит историю:

- время проверки;
- статус `up` или `down`;
- код HTTP, если он известен;
- время ответа;
- текст ошибки.

Одна цель имеет много результатов проверок: это связь one-to-many.

## Что улучшить в production-версии

1. Заменить SQLite на PostgreSQL.
2. Добавить Alembic для миграций схемы.
3. Вынести scheduler в отдельный worker.
4. Добавить retry с ограничением количества повторов.
5. Добавить Prometheus-метрики и Grafana.
6. Сделать учетные записи пользователей и роли.
7. Добавить уведомления в Telegram или email.
8. Ограничить срок хранения истории.
